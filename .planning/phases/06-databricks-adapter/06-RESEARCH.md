## Summary

1. dbt-databricks (>= 1.12.0) ships `{% materialization metric_view, adapter='databricks' %}`. The
   **model body is the metric view YAML**, not SQL and not config; the materialization wraps it as
   `create or replace view <rel> with metrics language yaml as $$ <body> $$`. Like Snowflake, **we
   generate the definition text**. dbt renders Jinja in the body, so `source: "{{ ref('x') }}"` gives
   the DAG edge (verified on Fusion: `depends_on` correct, compiled to `` "`analytics`.`marts`.`orders`" ``).
2. The YAML spec has versions **0.1** and **1.1**. Target **1.1** (needed for `comment`,
   `display_name`, synonyms) with nested ("snowflake schema") joins, both DBR **17.3+**; metric views
   need Unity Catalog. Joins are many-to-one `LEFT OUTER JOIN`s from `source` with `on` or `using`,
   nested `joins` for multi-hop. This maps cleanly onto the Phase 4 join closure.
3. Big differences from Snowflake: field/measure names are **one namespace per view, case-insensitive**
   (no per-table qualification), joined columns must be referenced as `<join>.<col>` (nested:
   `<join>.<subjoin>.<col>`), derived metrics compose with `MEASURE(<name>)`, non-additive dimensions
   become `window: [{order, range: current, semiadditive}]`, and there is no `PRIVATE`.
4. **The Phase 4 header line breaks the YAML.** A first line `-- Generated by dbt-s-layer ...` is not a
   YAML comment; PyYAML rejects the document (*verified*). The marker must become `# ...` (YAML comment)
   or a Jinja comment, and `output._is_generated` must accept it.
5. Fusion 2.0.8 parses and compiles metric view models **offline** (verified), warning `dbt9000` unless
   the model sets `static_analysis='off'` (verified). But Fusion's adapter **panics** on
   `adapter.clean_sql` and `adapter.yaml_quote_backtick_values` (verified with a probe model), and the
   Fusion copy of the materialization calls both, so **`dbt run` of a metric view on Fusion 2.0.8 is
   expected to fail** (inferred; the 2.1.0 dev build fixes one of the two, not `clean_sql`).
6. dbt-databricks 1.12.7 requires `dbt-core>=1.11.2,<1.12.6` (METADATA). The project's Core fixtures
   use dbt-core 1.12.6, so a Databricks Core test environment resolves to dbt-core **1.12.5**.

{% materialization metric_view, adapter='databricks' -%}
  {%- set existing_relation = load_relation_with_metadata(this) -%}
  {%- set target_relation = this.incorporate(type='metric_view') -%}
  {% set grant_config = config.get('grants') %}
  {% set tags = config.get('databricks_tags') %}
  {% set sql = adapter.clean_sql(sql) %}
  {{ run_pre_hooks() }}
  {% if existing_relation %}
    {% if relation_should_be_altered(existing_relation, target_relation) %}
      {% set configuration_changes = get_configuration_changes(existing_relation) %}
      {% if configuration_changes and configuration_changes.changes %}
        {% if configuration_changes.requires_full_refresh %}
          {{ replace_with_metric_view(existing_relation, target_relation) }}
        {% else %}
          {{ alter_metric_view(target_relation, configuration_changes.changes) }}
        {% endif %}
      {% else %}
        {% call statement('main') %} select 1 {% endcall %}
      {% endif %}
    {% else %}
      {{ replace_with_metric_view(existing_relation, target_relation) }}
    {% endif %}
  {% else %}
    {% call statement('main') -%}
      {{ get_create_metric_view_as_sql(target_relation, sql) }}

    {% set tblproperties = config.get('tblproperties') %}

{%- endmaterialization %}

## 2. Metric view YAML spec

Sources: "Metric view YAML syntax reference" (`docs.databricks.com/aws/en/uc-semantics/metric-views/
yaml-reference`, reached via `.../metric-views/data-modeling/syntax`), "Metric view feature
availability" (`.../feature-availability`), "Joins" (`.../joins`), "Advanced techniques"
(`.../advanced-techniques`), "Create" (`.../create`), SQL reference `CREATE VIEW`
(`.../sql/language-manual/sql-ref-syntax-ddl-create-view`). All HIGH unless noted.

### Versions and runtime

- `version` is required: "the version of the metric view YAML specification ... Use one of the
  supported specification versions". Versions: **0.1** (initial) and **1.1** (adds `comment`,
  `display_name`, `format`, `synonyms`; plus `cardinality`, window `offset`, `inclusive`/`exclusive`
  at DBR 18.1+).
- Metric views: DBR 16.4+, Unity Catalog only (`CREATE VIEW` reference: "METRICS ... Unity Catalog
  only"). Snowflake-schema (nested) joins and agent metadata (spec 1.1): DBR **17.3**. One-to-many
  joins, `rely`: 18.1. Parameters, wildcards: 18.2. Derived names: 19. SQL warehouses track the
  latest DBSQL, so only clusters care.
- Recommendation: emit `version: 1.1`; document DBR 17.3+ / any current SQL warehouse; use nothing
  that needs 18.x.

### Top level

`version` (req), `comment`, `source` (req; three-part name, metric view, or SQL query), `parameters`,
`filter` (SQL boolean, applies to all queries), `joins`, `fields` (synonym `dimensions`), `measures`,
`materialization` (metric-view acceleration via materialized views; unrelated to dbt's materialization;
not needed).

`fields` vs `dimensions`: "`fields` and `dimensions` are equivalent keywords ... Existing metric views
that use `dimensions` continue to work, and both keywords are accepted on new or updated
definitions." The UI editor and every dbt-databricks fixture emit `dimensions`. Recommend
**`dimensions`** (works everywhere; the doc does not say which runtime first accepted `fields`).

### Joins

Each join: `name` (alias, req), `source` (req), `on` (boolean expr) or `using` (column list),
`cardinality` (`many_to_one` default; `one_to_many` needs 18.1), nested `joins`, `rely`.

- "In a star schema, the `source` is the fact table and joins with one or more dimension tables using
  a `LEFT OUTER JOIN`. Metric views join the fact and dimension tables needed for the specific query."
- "The join must follow a many-to-one relationship. In cases of many-to-many, the first matching row
  from the joined dimension table is selected."
- In `on`, `source.` names the metric view source and the join `name` names the joined table; "If no
  prefix is provided in an `on` clause, the reference defaults to the joined table."
- Nested join conditions reference the parent join by its name:
  `on: customer.c_nationkey = nation.n_nationkey`; fields reference nested columns by dot-path:
  `expr: customer.nation.n_name`.
- `rely: {at_most_one_match: true}` (18.1) is an unvalidated promise; wrong results if false.
- Joined tables can't include `MAP` columns.
- The docs quote the key as `'on':` in several examples. Under YAML 1.1 rules an unquoted `on` key is
  the boolean `true` (PyYAML `safe_load` gives `{True: ...}`, *verified*). Always emit `"on":`.

### Fields and measures

- Field: `name`, `expr` (scalar SQL over source columns or earlier fields), `comment`, `display_name`
  (≤255 chars, 1.1), `format` (1.1), `synonyms` (≤10, 1.1).
- Measure: same plus `window`. "Measures are expressions that produce results without a pre-determined
  level of aggregation. They must be expressed using aggregate functions ... Measures can reference
  base columns in the source data, earlier-defined fields, or earlier-defined measures."
  Composition: `MEASURE(total_revenue) / MEASURE(order_count)`. Filtered aggregates:
  `SUM(o_totalprice) FILTER (WHERE o_orderstatus = 'O')`.
- "Names must be unique across fields and measures, ignoring case."
- `expr: customer` (a join name) "returns the full customer row as a struct" (joins page): a bare
  identifier equal to a join name resolves to the join, not a column (*inferred* precedence).
- No `PRIVATE`/hidden flag exists for fields or measures.

### Window measures

`window:` is a list of `{order, range, semiadditive, offset?}`; `order` names a field; `range` is
`current | cumulative | trailing <n> <unit> [inclusive|exclusive] | leading ... | all`
(`inclusive`/`exclusive` 18.1+, default `exclusive`); `semiadditive` is `first | last` ("how to
aggregate the measure when the order field is not included in the query's GROUP BY"). The semiadditive
example (account balances) is `SUM(balance)` with `window: [{order: date, range: current,
semiadditive: last}]`.

### Quoting rules (docs "Column name references", "Expressions with colons")

"Valid YAML values cannot start with a backtick" (so a rendered `` `cat`.`sch`.`t` `` must be quoted);
"Always use double quotes around expressions that include colons". Recommendation: emit **every
scalar as a YAML double-quoted string** (escape `\` and `"`, newlines as `\n`), which removes the
backtick, colon, `#`, `on`/`yes`/`no` and leading-`*`/`&`/`!` cases in one rule. Then run
`sentinels.escape_jinja` on exprs and comments as Phase 4 does. The body sits inside `$$ ... $$`, so
an expr or comment containing `$$` would end the definition early; inside a YAML double-quoted string
write `$` as `\x24` (PyYAML decodes `"$\x24"` to `$$`, *verified*; Databricks' YAML parser is
unknown, *inferred* standard).

## 3. Compiling and validating offline

- **Fusion 2.0.8**: parse and compile work with dummy credentials and no network (verified above).
  Compile proves Jinja, refs and DAG only; Fusion does not validate the YAML (static analysis is
  skipped for metric views).
- **dbt Core + dbt-databricks**: not run (would execute downloaded code). From source: the body has no
  adapter calls, `clean_sql`/`yaml_quote_backtick_values` are `@available.parse` and used only in the
  materialization, so `dbt parse` needs no connection and `dbt compile --no-populate-cache` should
  compile offline exactly as Phase 4 found for Snowflake (*inferred*, MEDIUM). The plain `dbt compile`
  will try to connect for cache population. Environment pin: dbt-core 1.12.5 (dbt-databricks 1.12.7
  caps `<1.12.6`).
- **YAML validity offline**: we can check our own output with a YAML parser in unit tests (PyYAML is
  present in the project venv; metricflow pulls it in, *inferred*), parsing with both `safe_load` and
  `BaseLoader` and asserting the structure. Databricks' own validation (`METRIC_VIEW_INVALID_VIEW_
  DEFINITION` and friends) needs a workspace.
- No offline Databricks metric view validator exists that we found.

## 4. Mapping MetricFlow → Databricks metric view

### Shape

Shape B from Phase 4 carries over and fits better here: the root semantic model is `source`, every
closure edge is a many-to-one join (the IR only builds joins toward primary/unique entities), hop-2
models become nested `joins` under their hop-1 parent. One `sem__<name>.sql` per semantic model, only
the root's metrics. (HIGH that it is expressible; MEDIUM that Databricks accepts every generated
shape, see Open questions.)

### Expressions on joined tables

In Snowflake each logical table has its own scope, so a joined table's `expr: amount * 100` just
works. In a metric view all exprs are in the source's scope: columns of a joined table must be written
`orders.amount`. The IR stores unqualified exprs. Options for the planner:

1. **Bare columns only (simplest):** a joined-table dimension whose expr is a bare identifier renders
   as `<join path>.<col>`; any other expr on a joined table is skipped with a WARN. Root exprs are
   copied verbatim.
2. **Qualify with the scanner:** use `semantic_views.scan_sql` plus the Snowflake renderer's
   `_references`/`_not_a_column` logic to prefix column identifiers. Fragile for function names,
   keywords, lambdas and type names; a wrong guess silently changes meaning.
3. **SQL-query join source:** `source: "SELECT <key>, <expr> AS <dim>, ... FROM {{ ref(...) }}"`
   for joined tables, then fields reference `orders.<dim>`. No rewriting, exprs stay verbatim, still a
   DAG edge. Costs: the docs recommend PK/FK `RELY` constraints for SQL-query sources with joins, and
   query pruning is unknown.

Recommend 1 for Phase 6 (warn-and-skip, consistent with the Snowflake key rule), with 3 as the
follow-up if users hit the warning.

### Name collisions and shadowing

- Names are case-insensitive and view-wide: error (as Phase 4 does for metric vs root dimension) when
  any two emitted field/measure names fold to the same lower-case string. With MetricFlow-style
  prefixes this only happens on genuine clashes (metric named like a root dimension).
- Shadowing: fields and measures can reference "earlier-defined fields", so a field `amount` with
  `expr: amount * 100` might change `SUM(amount)` in a later measure. The docs do not say whether a
  field name or a source column wins. Mitigations: emit measures with `source.`-qualified bare columns
  where the expr is a bare identifier, and keep the Phase 4 shadowing check for other exprs (adapted:
  names are view-wide, not per table). Needs a workspace test (Open question 3).
- A root column whose name equals a join name (`customer`) resolves to the join struct (docs' `expr:
  customer` example). Rendering root bare-identifier exprs as `source.<col>` avoids it.

### Identifiers

Field and measure names are YAML strings; Databricks needs backticks only when querying names with
punctuation. Emit metricflow's lower-case names as is. Reserved words (`order`) as field names:
allowed in YAML, queried as `` `order` `` (*inferred*; the `new_spec` fixture has entity `order`).
Exprs are copied verbatim (a Databricks project's YAML is Databricks SQL).

## Recommendations for planning

### Generated file (new_spec fixture, `sem__order_items.sql`)

```yaml
# Generated by dbt-s-layer from semantic model 'order_items'. Do not edit: change the semantic YAML and run `dbt-s-layer generate`.
{{ config(materialized='metric_view', static_analysis='off') }}

version: 1.1
source: "{{ ref('order_items') }}"
joins:
  - name: "orders"
    source: "{{ ref('orders') }}"
    "on": "source.order_id = orders.order_id"
dimensions:
  - name: "order"
    expr: "source.order_id"
  - name: "order_item"
    expr: "source.order_item_id"
  - name: "ordered_at"
    expr: "source.ordered_at"
  - name: "order__customer"
    expr: "orders.customer_id"
  - name: "order__ordered_at"
    expr: "orders.ordered_at"
measures:
  - name: "items_sold"
    expr: "SUM(quantity)"
```

Compiled with refs resolved, this parses with PyYAML `safe_load` and `BaseLoader` (verified with the
equivalent rendered text). Joins appear only when the closure has edges; nested joins indent under
their parent. Field order: root table first, then closure order, sorted by name within a table (as
Phase 4); measures: simple sorted, then derived in dependency order.

### Header / ownership

`-- Generated by dbt-s-layer ...` as line 1 makes the definition invalid YAML (verified with PyYAML:
`ScannerError: mapping values are not allowed here`). Use a YAML comment `# Generated by dbt-s-layer
...` (it reaches Databricks, harmless; dbt-databricks' diff ignores comments) or a Jinja comment
`{# Generated by dbt-s-layer ... #}` (stripped at compile). Either way `output._is_generated` must
accept the new first line for `sem__*.sql`, and `_semantic_header` needs an adapter-specific form.
Recommend the YAML comment: it mirrors the existing `_YAML_MARK` and survives into compiled code.

### Module layout

- `src/dbt_s_layer/databricks.py`: `render_databricks(spec) -> str`, YAML double-quoted scalar helper
  (with `$` → `\x24` and Jinja escaping), join tree from `relationships`, field naming, MEASURE()
  substitution for `DerivedMetricSpec.parts`, the window spec for `NonAdditiveSpec`, percentile rules.
  Hand-render the YAML (as `snowflake.py` hand-renders DDL); ruamel would re-quote `{{ ref('x') }}`
  unpredictably and byte stability matters.
- `semantic_views.py` changes the IR needs: entity name on `RelationshipSpec` (for `<entity>__<dim>`
  names); `MetricSpec.label` (if labels map to `display_name`); move the approximate-percentile skip
  out of `_simple_metric` into each renderer (Snowflake skips approx discrete, Databricks approx
  continuous); renderer-specific skips must still produce one WARN each, so give renderers a way to
  return warnings (today they only raise `SemanticViewError`, which drops the whole view).
- Dispatch: `{"snowflake": ..., "databricks": render_databricks}`; generalise the package check:
  Databricks WARN when `macro.dbt_databricks.materialization_metric_view_databricks` is absent from
  manifest.json (dbt-databricks < 1.12.0: `dbt run` would fail with no `metric_view`
  materialization). `doctor` reports it for Databricks targets.
- Clash check, companion YAML: unchanged from Phase 4 (sem__ names are adapter-neutral).

## Open questions (need a Databricks workspace)

1. Does Databricks accept the generated shape: `version: 1.1`, `dimensions:` keyword, quoted `"on":`,
   nested joins whose `on` references the parent join by name, `PERCENTILE_CONT ... WITHIN GROUP` and
   `PERCENTILE_DISC` and `APPROX_PERCENTILE` inside measures, `MEASURE()` composition with `NULLIF`?
2. Does Databricks' YAML parser decode `\x24` in double-quoted strings (the `$$` escape)?
3. Name resolution: does a field name shadow a source column of the same name inside a later measure
   or field expr? Does an unqualified column in a field resolve only against `source`, or also against
   joined tables when unambiguous?
4. Are reserved words (`order`) and names that equal a join name accepted as field names?
5. Does `dbt run` of a metric view fail on Fusion 2.0.8/2.0.9 as the `clean_sql` panic predicts, and
   does it on dbt Core 1.12.5 + dbt-databricks 1.12.7 succeed end to end (create, then rerun as
   no-op/replace)?
6. Semiadditive semantics vs MetricFlow's non-additive dimension (ties, NULLs, grouping by other
   fields), checked on real data.
7. Does `dbt compile --no-populate-cache` on Core + dbt-databricks really avoid every connection
   (not verified here because the adapter was not run)?

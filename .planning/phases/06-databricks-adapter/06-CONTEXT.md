# Phase 6: Databricks Adapter - Context

**Gathered:** 2026-10-19
**Status:** Ready for planning
**Source:** ROADMAP Phase 6, REQUIREMENTS SEMVW-03, 06-RESEARCH.md ("Recommendations for
planning"), the Phase 4 decisions this phase reuses (04-CONTEXT.md)

<domain>
## Phase Boundary

Generate one `sem__<semantic_model>.sql` per semantic model for Databricks targets. Each file is
the metric view YAML definition that dbt-databricks' `metric_view` materialization (>= 1.12.0)
wraps in `CREATE OR REPLACE VIEW ... WITH METRICS LANGUAGE YAML`, with `{{ ref() }}` calls for
every table it reads. It reuses the Phase 4 IR (`semantic_views.py`), clash check and companion
YAML.

**In scope:** the Databricks renderer (`databricks.py`), the IR changes it needs, adapter
dispatch, the ownership header for YAML bodies, the missing-materialization warning and its
`doctor` line, a Databricks fixture project with a compile test on both engines, README.

**Out of scope:** DuckDB (Phase 7), the features skipped below (v2 requirements), running on a
real Databricks workspace inside CI (the end-to-end run is a manual smoke test on the
maintainer's machine, as in Phase 4).
</domain>

<decisions>
## Implementation Decisions

- **Same shape as Phase 4.** One view per semantic model: the root is `source`, every closure
  edge is a many-to-one `joins` entry, hop-2 models nest under their hop-1 parent. Only the
  root's metrics. Diamonds keep the first path and warn (shared IR).
- **Spec version 1.1.** `version: 1.1` (needed for `comment` and `display_name`; nested joins
  need DBR 17.3+ anyway). README states the runtime requirement: Unity Catalog and DBR 17.3+ or
  a SQL warehouse that supports metric view spec 1.1.
- **File body.** Line 1 is a YAML comment with the ownership marker
  (`# Generated by dbt-s-layer from semantic model '<name>'. Do not edit: ...`): the Phase 4
  `--` line is invalid YAML (06-RESEARCH §Header). Then
  `{{ config(materialized='metric_view', static_analysis='off') }}`, a blank line, and the
  YAML: `version`, `comment` (when the root has a description), `source`, `joins` (when any),
  `dimensions`, `measures` (when any). `output._is_generated` accepts both marker forms.
  Hand-rendered YAML with double-quoted scalars (byte-stable; ruamel would re-quote Jinja);
  `$` in a scalar is written `\x24` so no expr can close the `$$` wrapper; every body goes
  through `sentinels.escape_jinja` and `postflight`; every snapshot is checked to load with
  `yaml.safe_load` once refs are rendered.
- **Field names.** Names are one case-insensitive namespace per view. Root dimensions and
  entities keep their names; a joined table's elements are named with MetricFlow's group-by path
  (`<entity>__<name>`, two hops `<entity>__<entity>__<name>`), which needs the entity name on
  `RelationshipSpec`. Two emitted names that fold to the same string are an error for that view
  (the view is skipped with a WARN, as Phase 4 does for name shadowing).
- **Exprs.** A root element's bare-identifier expr renders as `source.<col>` (a bare name that
  equals a join name would otherwise resolve to the join). Other root exprs are copied verbatim
  (a Databricks project's YAML holds Databricks SQL). A joined table's bare-identifier expr
  renders as `<join path>.<col>`; any other expr on a joined table is skipped with one WARN
  (SEMVW-V2-10 records the SQL-query join source that would lift this). The Phase 4 shadowing
  check is applied view-wide.
- **Joins.** `name` = lowercased semantic model name, `source: "{{ ref(...) }}"`,
  `"on": "<parent path>.<child col> = <join name>.<parent col>"` (`source.` at the top level).
  A semantic model named `source` cannot be a join name: that view is skipped with a WARN.
- **Labels.** `label` becomes `display_name` (dimensions, entities, measures). Descriptions
  become `comment`.
- **Measures.** sum, min, max, average (`AVG`), count, count_distinct, sum_boolean as Phase 4;
  median and continuous percentile `PERCENTILE_CONT(p) WITHIN GROUP (ORDER BY x)`, discrete
  `PERCENTILE_DISC`, approximate discrete `APPROX_PERCENTILE(x, p)`. Approximate continuous has
  no Databricks function: skipped with a WARN. The approximate-percentile skip moves from the
  builder into each renderer, and renderers can return warnings (not only raise).
- **Non-additive dimensions.** No `window_groupings`: `window: [{order: <dim field>, range:
  current, semiadditive: last}]` for `window_choice: max`, `first` for `min`. With
  `window_groupings`: skipped (shared, SEMVW-V2-06).
- **Derived and ratio metrics.** Same qualifying rules as Phase 4. Derived renders its `expr`
  with each input replaced by `MEASURE(<input>)`; ratio renders
  `MEASURE(<num>) / NULLIF(MEASURE(<den>), 0)`. Measures are emitted simple first (sorted), then
  derived in dependency order, since a measure can only use earlier ones.
- **Private metrics.** A metric view has no hidden measures. A private metric is emitted only when
  an emitted derived or ratio metric uses it, with one WARN saying it is visible; otherwise it is
  left out silently (it was never meant to be queried).
- **Skipped as in Phase 4 (one sorted WARN each).** Cumulative, conversion, metric filters,
  natural entities, derived/ratio metrics that do not qualify; `agg_time_dimension` dropped
  silently, `fill_nulls_with` / `join_to_timespine` dropped with a WARN.
- **Missing materialization.** On a Databricks target, when manifest.json has no
  `macro.dbt_databricks.materialization_metric_view_databricks` (dbt-databricks < 1.12.0),
  `generate`/`check` WARN, and `doctor --project-dir` reports it.
- **Fusion.** (Superseded by 06-VERIFICATION: `dbt build` of the metric views succeeds on
  Fusion 2.0.8 against a real workspace.) Fusion 2.0.8 parses and compiles the files offline, but its adapter does not
  implement two calls the materialization makes, so `dbt run` of a metric view needs dbt Core +
  dbt-databricks today (06-RESEARCH §5). README says so; the smoke test checks it.
- **Fixture and tests.** A `databricks_spec` project (Fusion) and a dbt Core twin if Core
  needs one, with a `databricks` target and dummy credentials; artifact sets keep the
  materialization macro id. Snapshot tests per artifact set, unit tests per mapping row, the YAML
  load check, and an integration test that compiles on Fusion and on Core (`--no-populate-cache`,
  dbt-core 1.12.5 + dbt-databricks 1.12.7), skipping cleanly when an engine is unavailable.
- **Real workspace.** After the PR is green, a smoke test on the maintainer's Mac against the
  `databricks` target: build the fixture, query each view with `MEASURE()`, compare the numbers
  with plain SQL, and settle 06-RESEARCH's open questions. Anything that fails is fixed in the
  PR before merge.

</decisions>

# dbt-s-layer (WIP)

dbt semantic-layer features for dbt Core / Fusion users, no dbt Cloud required.

`dbt-s-layer` is a Python package that reads dbt semantic YAML (via `semantic_manifest.json`) and code-generates two families of dbt models:

1. **Warehouse-native semantic views** (`sem__*.sql`) — Snowflake `SEMANTIC VIEW`, Databricks metric views, DuckDB semantic views
2. **Pre-aggregated exports** (`exp__*.sql`) — materialised from `saved_query` export blocks using MetricFlow's SQL rendering engine

A pre-commit hook keeps generated files in sync with YAML changes automatically.

## Status

Alpha. Under active development.

## Requirements

- Python 3.11+
- A dbt engine on `PATH` that writes `target/semantic_manifest.json` when you run `dbt parse`, either of:
  - [dbt Core](https://docs.getdbt.com/docs/core/installation-overview) 1.7 or later, which parses both the legacy and the new semantic YAML spec
  - [dbt Fusion](https://docs.getdbt.com/docs/fusion/install-fusion), which parses the new spec only

Run `dbt-s-layer doctor` to check what it finds. Add `--project-dir path/to/project` to also check that project's parse artifacts exist and are newer than its semantic YAML, and that the output directory can be written.

## Generating models

Run `dbt parse`, then:

```sh
dbt-s-layer generate --project-dir path/to/project
```

This writes the generated models and a `_semantic_views.yml` schema file to `models/semantic/`. Commit them alongside your semantic YAML. Running it again with the same inputs leaves the files byte-for-byte unchanged.

In CI, `dbt-s-layer check` (same options) exits 1 and lists the changed, missing and stale files when the committed models no longer match a fresh run. It writes nothing.

| Option | Default | |
|---|---|---|
| `--project-dir` | current directory | The dbt project. Its `target/` must hold fresh `dbt parse` artifacts. |
| `--output-dir` | `models/semantic` | Relative to `--project-dir`. Keep it under your `model-paths` so dbt builds the models. |
| `--adapter` | the adapter you parsed with | SQL dialect: `snowflake`, `databricks`, `duckdb`, `bigquery`, `postgres`, `redshift`, `trino` or `athena`. |
| `--target` | | Use this dbt target's adapter type from `profiles.yml` as the dialect. `--adapter` wins if both are given. |
| `--profiles-dir` | `DBT_PROFILES_DIR`, the current directory, the project, `~/.dbt` | Where to find `profiles.yml` for `--target`. |

In the output directory, dbt-s-layer owns the `exp__*.sql`, `sem__*.sql` and `_semantic_views.yml` files. Each starts with a `Generated by dbt-s-layer` line. Files it no longer generates are deleted. It won't overwrite a file with one of those names that lacks the header, and it leaves every other file alone. New and changed files are staged next to the output directory and moved into place only once all of them are written. A failed run leaves the directory as it was.

`generate` also refuses a model that would clash with one of yours, either by name or by building the same table (same custom schema and alias, compared case-insensitively).

## Exports

Each `export` of a `saved_query` becomes one model, `exp__<saved_query>__<export>.sql`: MetricFlow's SQL for the saved query, with every table it reads written as a `{{ ref() }}`, so the export sits in your DAG like any other model.

- `export_as: table` or `view` sets `materialized` (default `table`). An export without its own `export_as` uses the saved query's `config.export_as`.
- `alias` defaults to the export name.
- `schema`, if you set one on the export or the saved query, goes through your project's `generate_schema_name` like any dbt model schema. With dbt's default macro that means `<target schema>_<schema>`, where dbt Cloud would write to the schema exactly as named.
- The SQL dialect follows the adapter of the target you parsed with, unless you pass `--adapter` or `--target`.
- The schema file describes each export with its saved query's `description`.
- An entity, dimension or metric named like a reserved word of the dialect (`order`, `group`, ...) is quoted in the SQL, in the case the warehouse gives an unquoted name (`"ORDER"` on Snowflake), so the column keeps its usual name. MetricFlow itself leaves such names bare ([metricflow#2058](https://github.com/dbt-labs/metricflow/issues/2058)). SQL you write in an `expr` is used as written: quote a reserved word there yourself.

## Semantic views (Snowflake)

On a Snowflake target, each semantic model becomes one model, `sem__<semantic_model>.sql`, that
the Snowflake-Labs [`dbt_semantic_view`](https://github.com/Snowflake-Labs/dbt_semantic_view)
package builds as a Snowflake `SEMANTIC VIEW`. Databricks targets get metric views instead (see
[Metric views (Databricks)](#metric-views-databricks)). Other adapters get no `sem__` files yet
(DuckDB is planned) and one warning; their exports are generated as usual.

The model body is the `CREATE SEMANTIC VIEW` clause list. For `orders` it looks like this:

```sql
-- Generated by dbt-s-layer from semantic model 'orders'. Do not edit: ...
{{ config(materialized='semantic_view', static_analysis='off') }}

TABLES (
  orders AS {{ ref('orders') }}
    PRIMARY KEY (order_id),
  customers AS {{ ref('customers', v=2) }}
    PRIMARY KEY (customer_id)
)
RELATIONSHIPS (
  orders_to_customers AS orders (customer_id) REFERENCES customers (customer_id)
)
DIMENSIONS (
  orders.customer AS customer_id,
  orders."ORDER" AS order_id,
  orders.ordered_at AS ordered_at,
  customers.country AS country,
  customers.customer AS customer_id
)
METRICS (
  orders.order_count AS COUNT(DISTINCT order_id),
  orders.revenue AS SUM(amount),
  average_order_value AS orders.revenue / NULLIF(orders.order_count, 0)
)
```

- **Tables.** The semantic model, plus every semantic model MetricFlow could join to it: through
  its primary, unique or foreign entities to a model where that entity is primary or unique, up
  to two hops. Each is a `{{ ref() }}`, so the view sits in your DAG after the models it reads.
  When two join paths reach the same model, the first (in name order) is kept and you get a
  warning.
- **Keys and relationships.** Primary and unique entities become `PRIMARY KEY` and `UNIQUE`, and
  each join a `RELATIONSHIPS` entry. Snowflake keys must be columns, so an entity whose `expr` is
  an expression is neither a key nor a join (with a warning).
- **Dimensions.** Every dimension of every table, plus its primary, unique and foreign entities,
  each as `<table>.<name> AS <expr>`.
- **Metrics.** The semantic model's own simple metrics (`sum`, `min`, `max`, `average`, `count`,
  `count_distinct`, `sum_boolean`, `median` and `percentile`), with `PRIVATE` for private metrics
  and `NON ADDITIVE BY` for a non-additive dimension. Ratio and derived metrics whose inputs are
  all simple metrics of the same semantic model become view-level metrics.
- **Descriptions** become `COMMENT`s. Names that are Snowflake keywords (`order`, `group`) are
  written as upper-case quoted identifiers, which name the same thing.

dbt-s-layer skips the semantic view of a semantic model where Snowflake would read an expression
differently from MetricFlow: Snowflake resolves a bare name to a dimension or metric of the view
before a column, so a dimension `amount AS amount * 100` would change a metric `SUM(amount)`.
`generate` prints a `WARN semantic views: skipped sem__<name>: ...` line saying why, and writes
the exports and the other views as usual. Rename the dimension, or make its `expr` exactly its
column. A metric named like a dimension of its semantic model is skipped the same way.

### Install the package

Add `dbt_semantic_view` to your `packages.yml` and run `dbt deps`:

```yaml
packages:
  - package: Snowflake-Labs/dbt_semantic_view
    version: [">=1.0.6", "<1.1.0"]
```

If your network blocks the hub's GitHub downloads, the `git:` form works too:

```yaml
packages:
  - git: https://github.com/Snowflake-Labs/dbt_semantic_view.git
    revision: v1.0.6
```

Without it, `dbt parse` and `dbt compile` still succeed but `dbt run` fails on the `sem__`
models, so `generate`, `check` and `doctor` warn when it is missing. `static_analysis='off'`
stops Fusion from parsing the DDL as a query. The generated models compile on dbt Core 1.12 and
Fusion 2.0.8; they have not yet been run against a Snowflake account.

## Metric views (Databricks)

On a Databricks target, each semantic model becomes `sem__<semantic_model>.sql`, which
dbt-databricks 1.12.0 or later builds as a Unity Catalog
[metric view](https://docs.databricks.com/aws/en/metric-views/) with its `metric_view`
materialization. No extra package is needed. The model body is the metric view's YAML
definition. For `orders` it looks like this:

```yaml
# Generated by dbt-s-layer from semantic model 'orders'. Do not edit: ...
{{ config(materialized='metric_view', static_analysis='off') }}

version: 1.1
comment: "One row per order."
source: "{{ ref('orders') }}"
joins:
  - name: "customers"
    source: "{{ ref('customers', v=2) }}"
    "on": "source.customer_id = customers.customer_id"
dimensions:
  - name: "order"
    expr: "source.order_id"
  - name: "ordered_at"
    expr: "source.ordered_at"
  - name: "customer__country"
    expr: "customers.country"
measures:
  - name: "order_count"
    comment: "Distinct orders."
    expr: "COUNT(DISTINCT source.order_id)"
  - name: "revenue"
    display_name: "Revenue"
    expr: "SUM(source.amount)"
  - name: "average_order_value"
    expr: "MEASURE(`revenue`) / NULLIF(MEASURE(`order_count`), 0)"
```

It covers the same tables, dimensions and metrics as the Snowflake view, with these
differences:

- **Joins.** The semantic model is the metric view's `source`; the models it joins to are
  `joins`, and a second hop is nested under the first.
- **Names.** A metric view has one namespace for its dimensions and measures, so a joined
  model's dimensions are named the way MetricFlow names them in a query: `customer__country`,
  or `order__customer__country` two hops away. Two names that differ only in case are an error,
  and that view is skipped with a warning.
- **Expressions.** A plain column is written `source.<column>` or `<join>.<column>`. Any other
  `expr` on the semantic model itself is copied as written, so write it in Databricks SQL. A
  joined model's dimension whose `expr` is not a plain column is left out with a warning.
- **Measures.** Ratio and derived metrics use `MEASURE()` on their inputs. A non-additive
  dimension becomes a `window` with `semiadditive: last` (`window_choice: max`) or `first`
  (`min`). Labels become `display_name` and descriptions `comment`.
- **Private metrics.** Metric views have no hidden measures. A private metric is left out,
  unless a ratio or derived metric uses it: then it is in the view, with a warning saying so.
- **A semantic model named `source`** cannot be joined, because the root table has that name;
  views that would join it are skipped with a warning.

Metric view spec 1.1 needs Unity Catalog and Databricks Runtime 17.3 or later (or a SQL
warehouse that supports it). With dbt-databricks older than 1.12.0, `dbt parse` and
`dbt compile` still succeed but `dbt run` fails on the `sem__` models, so `generate`, `check`
and `doctor` warn. The generated models compile on dbt Core 1.12.5 with dbt-databricks 1.12.7
and on Fusion 2.0.8. Fusion 2.0.8 cannot run them yet (its Databricks adapter does not
implement two calls the materialization makes), so use dbt Core to `dbt run` metric views.

## What is left out of semantic and metric views

Each of these is skipped with one warning naming it; the rest of the view is still generated.

| Left out | Why |
|---|---|
| Cumulative metrics | A window metric is partitioned by the queried dimensions, not a time spine. Use an export. |
| Conversion metrics | No semantic view equivalent. |
| Metric filters (on a metric or its input) | Would need the `{{ Dimension(...) }}` filter rendered against the view's columns. |
| Non-additive dimensions with `window_groupings` | The warehouse picks the last rows per queried dimensions, not per entity. |
| Natural entities (validity windows) | No semantic view equivalent. |
| Approximate discrete percentiles (Snowflake) | Snowflake has no such function. |
| Approximate continuous percentiles (Databricks) | Databricks has no such function. |
| Ratio and derived metrics with an offset, a filter, or inputs from another semantic model or another derived metric | Only metrics of the same view can be combined without changing their meaning. |
| `fill_nulls_with`, `join_to_timespine` | Ignored (with a warning); the metric is generated without them. |

## Pre-commit hook

The `dbt-s-layer` hook regenerates the models when you commit a change to your semantic YAML, so the generated files never fall behind. Add it to your repository's `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/s-layer/dbt-s-layer
    rev: develop  # no release tag yet: pin a commit SHA, and run `pre-commit autoupdate` once tags exist
    hooks:
      - id: dbt-s-layer
```

Then `pre-commit install` (or `prek install`). On a commit that stages semantic YAML, the hook:

1. finds the dbt project of each staged file: the nearest `dbt_project.yml`, unless a project above it lists that directory as a `local:` package in `packages.yml` or `dependencies.yml`, in which case the installing project (a project in a subdirectory works, and a package that names no `profile` belongs to the nearest project above it that does),
2. runs `dbt parse` in it. A project that declares legacy-spec `semantic_models:` (itself, or in a package it installs) is parsed with dbt Core, since Fusion ignores them; the hook stops with an error if `dbtf`/`dbt` on `PATH` offers no dbt Core >= 1.7. Any other project is parsed with `dbtf` if it is on `PATH`, else `dbt`. `--dbt` overrides both,
3. runs `dbt-s-layer generate`. If `semantic_manifest.json` lacks a semantic model your YAML declares (a parse with the wrong engine), the hook fails without writing or deleting anything,
4. fails the commit if it wrote, changed or deleted anything, and lists the files. Stage them (`git add`) and commit again; the second run changes nothing and passes.

Only files that hold a `semantic_models:`, `semantic_model:`, `metrics:`, `saved_queries:` or `time_spine:` key, a `dbt_project.yml`, or a generated file trigger it. A commit without any of them skips the hook in a fraction of a second. A hand edit to a generated file is put back. Deleting a semantic YAML file does not trigger the hook (pre-commit only passes files that exist), so keep `dbt-s-layer check` in CI as well.

`dbt parse` needs a profile, as it always does. The hook passes `generate`'s options through `args`, and has two of its own:

```yaml
      - id: dbt-s-layer
        args: [--target, dev, --profiles-dir, analytics/profiles, --dbt, .venv/bin/dbt]
```

| Option | |
|---|---|
| `--dbt` | The executable that parses, for example a dbt Core in a virtualenv that is not activated. Paths are relative to the repository root. |
| `--no-parse` | Don't run `dbt parse`: something else parses first (another hook). `generate` still refuses artifacts older than the YAML. |
| `--project-dir`, `--output-dir`, `--target`, `--adapter`, `--profiles-dir` | As for `generate`. `--target` goes to `dbt parse` too. The hook finds `profiles.yml` once (`--profiles-dir`, else `DBT_PROFILES_DIR`, the repository root, the project, `~/.dbt`) and passes that directory to `dbt parse` as `--profiles-dir`, so both read the same file. |

pre-commit installs dbt-s-layer in its own environment, so it never touches the dbt you run. Your dbt engine still has to be on `PATH` (or named with `--dbt`).

**Speed.** On a project with 100 semantic models and 50 exports (`scripts/make_scale_project.py`), on a 4-core Linux machine, the hook takes 4.0 to 4.4 s after a YAML edit with dbt Fusion 2.0.8, whose `dbt parse` takes 0.7 s. dbt Core's own `dbt parse` takes 5.4 to 6.6 s on the same project (more than half of it is dbt's start-up), so with dbt Core the hook takes 10 to 12 s. Saved queries are rendered in parallel on Linux and macOS (in forked processes, and only while dbt-s-layer runs a single thread); set `DBT_S_LAYER_JOBS=1` to use one process. If a worker process dies (out of memory, say), the run fails with an error that suggests that setting.
